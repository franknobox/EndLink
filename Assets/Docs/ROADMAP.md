# EndLink Roadmap

EndLink 是一个早期 3D 连携战斗 demo，目标参考类似《异度之刃》和《明日方舟：终末地》的小队协同战斗体验。当前阶段仍处在白模验证期，优先建立单人控制、镜头、状态机和战斗基础能力，再逐步扩展到连携与小队表现。
目前优先做好单人ARPG/ACT体验，参考《尼尔：机械纪元》、《无限机兵》、《只狼》及其他魂类游戏。

文档更新原则：不变动结构，实际开发与计划有冲突则调整文档表述。
开发规划：有新增就新增，做完了就去掉，表述简洁。


## 近期 Review 反馈


### 主要发现

- **P0：ACT 命中表现接近空白。** 当前尚未形成 Hitstop、Cinemachine Impulse、手柄震动、音效和 VFX 等通用反馈链路。轻重攻击、格挡、弹反、反应与奥义之间仍缺少可感知差异。
- **P0：玩家有状态机，但动作深度不足。** 三段普攻尚未形成三个有差异的正式动作，攻击状态主要只处理下一段普攻缓存；普攻、技能、闪避和格挡之间缺少取消与优先级关系。
- **P1：敌人目前只有一种压力模型。** 还没有远程压制、浮空单位、精英或 Boss。当前更缺第二种战斗角色和可收尾的精英战。
- **P1：自动化保障明显不足。** 现有测试覆盖与运行时代码规模不匹配，连段、动作取消、格挡结算、标签反应、连携窗口和协同率等关键边界尚未形成稳定回归保护。

### 程序可先行

- 通用战斗反馈调度基础已建立；之后为实际 Action 配置反馈资产。
- 玩家动作取消策略、硬锁目标切换、锁定移动与定向闪避，已完成逻辑骨架。
- 敌人韧性、平衡、失衡已建立，攻击预警和远程攻击执行基础 待做。
- 对稳定纯逻辑边界补充 EditMode 测试，并在关键场景流程稳定后增加少量 PlayMode 冒烟测试。

- 当前继续保留 Fast Action 与 SoulsLike 双预设实验，在手感方向确定前不引入强绑定某一种模式的大型系统。


## 后续开发规划


### 11. 编辑器工具优化

内容：
- 整理优化现有工具。增加场景配置体检、键位绑定面板。
- 建立场景联调窗口，按玩家、镜头、战斗和敌人分类集中调整高频参数，并标明参数的真实来源组件。
- 支持 Play Mode 参数差异记录，在退出播放后选择性将白名单配置应用回场景，不保存运行时状态或第二套数据。
- 增加 Action 与动画校准能力，检查动画事件和动作时序，并在 Scene View 显示 Hitbox、攻击范围与位移信息。
- 增加 Playtest 快捷控制，用于恢复生命、清除冷却与标签、调整协同率、重置敌人和返回出生点。


### 12. 单人向战斗 UI 与键位确定

内容：
- 按单人 ARPG / ACT 战斗方向整理 HUD 信息层级，明确生命、动作技能、冷却、锁定、防御反馈和奥义等必要显示。
- 确定键鼠与手柄的默认键位，解决攻击、技能、闪避、冲刺、格挡、交互、锁定和奥义之间的输入冲突。
- UI 统一读取 Input System 的实际绑定并显示对应键位，避免界面文本与运行时配置不一致。


### 13. 三种武器形态基础+对应交互机制

内容：
- 建立三种武器形态及控制器；当前设计定位分别为标准、射击、重刃。实现了远程瞄准攻击。
- 为每种形态配置独立的普攻连段、主动技能和基础能力规则。
- 建立形态切换许可、切换请求和变化事件，先支持非动作状态安全切换，后续再接攻击派生与取消窗口。
- 实现并完善对应的基于武器不同形态攻击的交互机制。


### 14. 动画与游戏表现衔接优化

计划内容：
- 动画播放基础：统一 Avatar、Root Motion、原地动画、循环姿势、状态切换和播放速度配置，解决模型错误问题。
- 逻辑与空间对齐：校准角色逻辑根、视觉模型、角色控制器、锁定点、Hitbox、地面高度和攻击朝向，避免动画位置与碰撞体脱节。
- 动作时序对齐：按动画关键帧调校 `startup / active / recovery` 对应实际动作；稳定后再逐步接入动画事件驱动判定窗口。
- 动作节奏调校：调整动画速度、过渡时间、攻击冷却、移动速度、攻击位移、追踪、击退和硬直时间，使表现连贯清晰。
- 攻击可读性：强化敌人出手前的预备动作、攻击方向、技能差异、危险范围和命中反馈，避免重要动作表现不明显。
- 打击表现补充：逐步加入短暂卡肉、镜头冲击、手柄震动、材质闪烁、武器/肢体拖尾、命中特效、落地冲击、音效和屏幕反馈。
- 联调与验证：先完成 APS01 敌人的完整动画战斗闭环，再检查不同帧率、坡地、转向、受击打断和围攻情况下的稳定性。

阶段原则：
- 当前仍以数据时序驱动战斗判定，动画事件在动作资源和流程稳定后逐步接管关键时点。
- 卡肉、镜头冲击、手柄震动、材质反馈和基础 VFX 不依赖最终动画 Clip，可以提前搭建轻量可调的通用接口。


## 场景与 Layer 规范（暂）

当前先统一白模与开发场景的基础组织方式，后续根据实际关卡规模和碰撞需求继续调整。

场景顶层结构：

```text
SceneRoot
├─ _Systems         世界、小队、战斗、复活等场景级系统
├─ _Gameplay        玩家、队友、敌人、交互物和出生点
├─ _Environment     几何、碰撞、NavMesh 和关卡结构
├─ _Presentation    相机、灯光、VFX 和 UI
└─ _Debug           只用于开发期的调试物体
```

约定：
- `SceneRoot` 及各分类根保持位置零、旋转零、缩放一，不通过分类根缩放实际内容。
- 角色与敌人使用“逻辑根 + `Visuals`”结构；状态机、生命、碰撞、移动和战斗组件放在逻辑根，模型、Animator 和纯表现放在 `Visuals`。
- 可复用内容优先做成 Prefab，场景实例只保存位置、引用和少量关卡差异配置。
- Layer 只表达物理碰撞、射线和范围查询关系；战斗状态继续使用 `CombatTag`，不要用 Unity Layer 代替。
- 交互扫描要求交互 Collider 所在物体使用 `Interactable` Layer；不要求所有视觉子物体继承该 Layer。
- 玩法对象不应长期停留在 `Default` Layer；纯视觉子物体可以保持 `Default`，除非有明确的物理查询需求。

当前 Layer 用途：

| Layer | 用途 |
|---|---|
| `Default` | 纯视觉、第三方资源或暂未分类物体。 |
| `TransparentFX` | 需要独立渲染或查询控制的透明表现。 |
| `Ignore Raycast` | 不参与常规射线检测的表现物体。 |
| `Player` | 主角逻辑根和实体碰撞。 |
| `Water` | 水面及水相关查询。 |
| `UI` | Canvas UI。 |
| `Interactable` | 可被 `WorldInteractor` 扫描的交互碰撞体。 |
| `Environment` | 地面、墙体、门框和其他场景实体碰撞。 |
| `Enemy` | 敌人逻辑根和实体碰撞。 |
| `Ally` | 队友逻辑根和实体碰撞。 |

后续：
- 根据实际命中检测和 Physics 碰撞矩阵需求，再决定是否增加独立 `Hitbox` / `WorldTrigger` Layer，暂不提前扩张。
- 建立正式 Physics Collision Matrix，明确玩家、队友、敌人、环境、交互物和 Hitbox 的碰撞关系。
- 在 Editor Validator 中增加场景层级、重复系统、Missing Reference、Layer、Collider、NavMesh 和常见接线检查。
